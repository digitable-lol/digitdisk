# digitdisk — куда ушло место, как себя чувствует машина и что можно убрать

digitdisk печатает две картины машины — **куда ушло место на диске** (каталоги
по размеру и самые крупные файлы) и **как машина чувствует себя прямо сейчас**
(процессор, память, диск, сеть) — и умеет действовать по первой из них:
`clean` убирает файлы, в три шага, ни один из которых не бывает неожиданностью.

`status` и `analyze` только читают. `clean` показывает план и без `--apply` не
трогает ничего; убранное уходит в корзину внутри указанного дерева и
возвращается командой `restore`; стирание — отдельная команда с отдельным
подтверждением. **Убирается не «похожее» и не «по маске»**: ровно то, чему
решающий слой в `core/` вынес приговор «МожноУбрать» — а про него доказано, что
он не достаётся ничему, кроме разрядов Кэш, Журнал и Сборка.

Конкретные места — кэш npm, кэш сборки Go, производные данные Xcode — digitdisk
знает **справочником**: отдельным файлом данных, который правится без
пересборки. Справочник называет разряд; приговор по-прежнему выносит ядро, и
пороги, каталоги, ссылки и хранилища, адресуемые содержимым, судятся ровно как
прежде. Что сказать «сюда не лезь» — [защитный список](#защитный-список);
чем кончались прошлые уборки — `digitdisk history`.

## Из чего состоит

```
core/       показатели как спецификация на flang и напечатанный из неё Go в core/out-go
host/       хозяин на Go: системные вызовы, командная строка, вывод
host/internal/places/places.conf   справочник известных мест: данные, не код
packaging/  формула Homebrew
scripts/    сборка выпуска
tools/      лицензионный сторож
docs/       заметки, которым не место на этой странице
```

Разделение и есть всё устройство. Всё, что решается без обращения к
операционной системе, решается в `core/`: спецификация на flang, проверяемая
прогонами самого flang и **печатаемая** в Go. Всё, что без операционной системы
не решается, — обход каталогов, `statfs`, чтение счётчиков — рукописный Go в
`host/`. Ядро не открывает файлов; хозяин не решает, что значит число.

`core/out-go` печатается, а не пишется. Правка руками теряется при следующей
печати — см. [`AGENTS.md`](AGENTS.md).

## Установка

**Готовые двоичные файлы: Linux (x86-64, arm64) и macOS (Apple Silicon,
Intel).** Все четыре собираются одной кросс-сборкой на Linux, с выключенным
CGO и повторимым отпечатком — см. [macOS](#macos) ниже.

### Homebrew

```bash
brew install digitable-lol/tap/digitdisk
digitdisk --version
```

Формула ставит готовый двоичный файл выпуска. Она ничего не собирает на машине
поставившего и не требует Go. Исходник формулы —
[`packaging/homebrew/digitdisk.rb`](packaging/homebrew/digitdisk.rb); копия,
которую читает brew, лежит в
[digitable-lol/homebrew-tap](https://github.com/digitable-lol/homebrew-tap).

### Готовый двоичный файл

```bash
V=0.1.0; A=amd64          # или A=arm64
base=https://github.com/digitable-lol/digitdisk/releases/download/v$V
curl -fsSLO $base/digitdisk-$V-linux-$A.tar.gz
curl -fsSLO $base/SHA256SUMS
sha256sum --check --ignore-missing SHA256SUMS
tar -xzf digitdisk-$V-linux-$A.tar.gz
sudo install -m 0755 digitdisk-$V-linux-$A/digitdisk /usr/local/bin/digitdisk
```

Суммы сверяются до распаковки, а не после. Формула прикладывается к тому же
выпуску, поэтому оба пути ставят одни и те же байты.

### Сборка из исходников

Для сборки из чистого клона хватает Go: напечатанный Go лежит в дереве.
Собирается изнутри `host/` — модуль там, в корне дерева модуля нет.

```bash
cd host && go build -tags flangcore -o ../digitdisk .
```

Признак `flangcore` и есть то, что кладёт ядро на flang внутрь двоичного файла.
Без него хозяин собирается с заглушкой, которая считает, но не решает;
`digitdisk --version` называет, что внутри, — гадать не приходится.

<a id="macos"></a>

### macOS: те же показатели, другой источник

Хозяин собирается и работает на macOS, arm64 и x86-64. Факты он берёт из
`sysctl(3)`, `getfsstat(2)`, маршрутного сокета и документированных функций
`libSystem` вместо `/proc` и `/sys`; ядра на flang это не касается вовсе — оно
никогда и не знало, что такое системный вызов.

```bash
cd host && GOOS=darwin go build -tags flangcore -o ../digitdisk .
```

**Почему без cgo.** Обычный способ позвать функцию на C из Go — cgo, и он
закрыл бы выпуск: четыре двоичных файла собираются на одной машине под Linux и
сверяются с собственной второй сборкой байт в байт, а cgo кончает оба свойства
разом. Поэтому вызовы делаются так же, как их делает сама стандартная
библиотека Go на macOS: символ объявляется динамическим импортом, к нему ведёт
короткая заглушка на ассемблере, а вызов уходит через `syscall.syscall6`.
Компоновщик Go записывает импорт в файл Mach-O, загрузчик системы связывает его
с `libSystem` при старте — ровно так же, как связывает импорты, которые уже
нужны рантайму. Никакого мака для сборки не нужно; нужен он только для проверки.

**Как проверяется раскладка.** Разбор структур написан по заголовкам Apple, а не
по чужим исходникам, и ни одно число не печатается, пока его происхождение не
подтверждено на самой машине:

| Что читается | Чем доказано, что читается правильно |
|---|---|
| запись о процессе (`kinfo_proc`) | свой номер процесса, свой родитель и свой пользователь оказались там, где мы их ждём |
| память и потоки процесса (`proc_taskinfo`) | ядро само сказало, сколько байт записало; свой процесс держит страницы и имеет хотя бы один поток |
| командная строка (`KERN_PROCARGS2`) | своя командная строка совпала со словами `os.Args`, которые рантайм получил другой дорогой |
| разбивка памяти (`vm_statistics64`) | ни один счётчик страниц не больше, чем страниц у машины; страницы упреждающего чтения не больше свободных, в которые ядро их и складывает; сумма непересекающихся долей сходится с `hw.memsize` с точностью до трети процента |
| доля занятого процессора | доля считается отношением двух разностей, поэтому не зависит ни от какой частоты счёта |
| счётчики интерфейсов (`if_data64`) | MTU совпал с тем, что называет стандартная библиотека |

Не сошлось — поле пустое, а не напечатано наугад. Сверх того, на каждый толчок
в дерево эти же самопроверки прогоняются на живых маковских бегунках GitHub, на
Apple Silicon и на Intel: `.github/workflows/check.yml` не только собирает, но и
снимает снимок и ищет в нём числа.

Что на macOS измеряется и каким вызовом:

| Показатель | Источник |
|---|---|
| узел, ядро, выпуск, модель | `sysctl` `kern.hostname`, `kern.osrelease`, `kern.version`, `kern.osproductversion`, `kern.osversion`, `hw.machine`, `hw.model` |
| время работы | `sysctl kern.boottime` (`struct timeval`) |
| средняя загрузка, ядра | `sysctl vm.loadavg` (`struct loadavg`), `hw.logicalcpu` |
| доля занятого процессора | `host_statistics(HOST_CPU_LOAD_INFO)` |
| память: всего и своп | `sysctl hw.memsize`, `hw.pagesize`, `vm.swapusage` (`struct xsw_usage`) |
| память: свободная, кэш, доступная, занятая, закреплённая, сжатая | `host_statistics64(HOST_VM_INFO64)` (`struct vm_statistics64`) |
| процессы: список и всего | `sysctl kern.proc.all` (`struct kinfo_proc`) |
| память, потоки, работающие потоки и процессорное время процесса | `proc_pidinfo(PROC_PIDTASKINFO)` (`struct proc_taskinfo`) |
| командные строки процессов | `sysctl {CTL_KERN, KERN_PROCARGS2, pid}` |
| диски | `getfsstat(2)` (`struct statfs`) |
| интерфейсы и адреса | `net.Interfaces` |
| счётчики интерфейсов | `sysctl NET_RT_IFLIST2` (`struct if_data64`) |

«Занято» и «доступно» — две стороны одного утверждения: память, которая не
свободна и не файловый кэш, занята. Это то же чтение, что даёт `free(1)` на
Linux, и отчёт печатает арифметику рядом с числом.

**Чего на маке нет и почему.** Двух видов, и это разные виды:

- **Закрыто правами, а не языком.** Память, потоки и командную строку процесса
  *другого пользователя* ядро не отдаёт никому, кроме администратора: оно
  сверяет владельца и отказывает. Под `sudo` эти строки заполняются; ничем
  другим — нет.
- **Система не публикует.** Температура кристалла снимается SMC через IOKit, и
  документированного интерфейса к нему Apple не публикует: в ходу
  восстановленная разбором структура. Число, прочитанное так, было бы догадкой
  с единицей измерения, поэтому его нет.

В отчёте они названы одной строкой, без объяснений. Объяснения — по
`digitdisk status --why` и в `--json`.

Ещё две маковские особенности, которые видно в отчёте: обход `/` без
`--cross-device` останавливается на `/System/Volumes/Data`, потому что система и
данные — две разные файловые системы; а каталог, закрытый механизмом
приватности, считается как «нет доступа» — так же, как нечитаемый каталог на
Linux.

Чтобы перепечатать ядро, дополнительно нужен
[flang](https://github.com/digitable-lol/flang), и только когда изменилась
спецификация:

```bash
make -C core            # проверка, печать в core/out-go и core/out-c, сверка
```

Архивы выпуска собирает
[`scripts/build-release.sh`](scripts/build-release.sh): он собирает каждую цель
дважды и отказывается паковать, если сборки разошлись, — тот же коммит и тот же
Go дают тот же архив побайтово.

## Запуск

```bash
./digitdisk                  # без подкоманды: то же, что `status`, со всеми его умолчаниями
./digitdisk analyze <путь>   # куда ушло место: каталоги по размеру, самые крупные файлы
./digitdisk status           # как себя чувствует машина: процессор, память, диск, сеть
./digitdisk places           # что инструмент знает о конкретных кэшах и что из этого есть здесь
./digitdisk history <путь>   # чем кончались прошлые уборки под этим корнем
./digitdisk --version        # версия, хеш сборки, инструментарий, решающий слой
./digitdisk --help           # подкоманды и ключи, по строке на каждую
man digitdisk                # справочник: подкоманды, ключи, файлы, примеры, коды возврата
```

Все четыре картины принимают `--json`. Ни одна из них не пишет. Слово, которое
подкоманде не соответствует, отвергается с кодом 2, а не толкуется; ключ на
месте подкоманды относится к `status`, поэтому `digitdisk --json` и
`digitdisk status --json` — одна и та же команда.

### Уборка, в три шага

```bash
./digitdisk clean <путь>                    # план: что, сколько, почему. Ничего не тронуто.
./digitdisk clean <путь> --apply            # перенос в <путь>/.digitdisk-trash/<метка>/
./digitdisk restore <корзина>               # вернуть всё обратно
./digitdisk purge <корзина> --confirm N     # стереть. Это уже необратимо.
```

По умолчанию — безобидное: `clean` без `--apply` не открывает на запись ни
одного файла и даже не создаёт корзину. Узнать, что инструмент сделал бы, не
должно означать «дать ему это сделать».

`--apply` — это `rename(2)` в корзину внутри того же дерева. Поэтому он
мгновенный и обратимый — и поэтому **не освобождает ни байта**: файлы остаются
на диске под другим именем. Место освобождает только `purge`; он требует
`--confirm N`, где N — ровно столько файлов, сколько в корзине, и в сообщении об
ошибке этого числа нет: его берут из плана, который печатает `purge` без ключа.
Подтверждение, которое можно дать не глядя, ничего не подтверждает.

В каждой корзине лежит `journal.json`: что убрано, откуда, сколько байт, когда и
куда перенесено. Он пишется **до** того, как сдвинулся первый файл, — обрыв на
середине оставляет корзину, которую `restore` всё равно разберёт обратно, — и
переживает `purge` как запись о том, чего больше нет.

Файл, изменившийся между обходом и переносом, не переносится. digitdisk
запоминает устройство, узел, размер, время изменения и права каждого файла,
сверяет их перед тем, как тронуть, и отказывается по имени причины — «размер
изменился (был 25 Б, стал 30 Б)», — вместо того чтобы убрать то, чего он больше
не узнаёт.

**План читается человеком.** Перечень режется ключом `--top` (по умолчанию 15,
как у `analyze`; `--top 0` — весь список) и кончается строкой «…и ещё N файлов
на M байт». Счёт при этом полный: итог, байты и разбивка по разрядам считаются
по всему плану и от `--top` не зависят — сводка, которая менялась бы вместе с
высотой экрана, была бы сводкой про экран. Под `--json` список едет целиком:
`--json` — это как зовут инструмент скрипты, и урезанный список работ сделал бы
`clean --json | jq` тихо неверным.

<a id="справочник-известных-мест"></a>

### Справочник известных мест

Правила ядра знают, что такое кэш ВООБЩЕ: составляющая пути называется
`.cache`, `Caches`, `cache`. Этого хватает, чтобы узнать кэш, и не хватает,
чтобы узнать кэш **npm**: его хранилище — `~/.npm/_cacache`, и составляющей со
словом `cache` там нет ни одной. Недостающее знание — это СПИСОК МЕСТ, а список
— это данные.

```bash
./digitdisk places                      # весь справочник и что из него есть здесь
./digitdisk places --json               # то же машине
./digitdisk clean <путь> --places Ф     # свой справочник вместо встроенного
./digitdisk clean <путь> --no-places    # судить одними приметами, как до 0.4.0
```

Справочник живёт в
[`host/internal/places/places.conf`](host/internal/places/places.conf), едет
внутри двоичного файла как значение по умолчанию и заменяется целиком — ключом
`--places` или файлом `~/.config/digitdisk/places.conf`. Строка справочника
такова:

```
разряд | якорь | система | путь | переменная | имя | источник
кэш|дом|все|.npm//_cacache|npm_config_cache|npm: кэш загрузок|https://docs.npmjs.com/...
```

Последнее поле обязательно, и это не украшение: **каждая строка взята из
документации самого инструмента**, и место попадает в справочник только тогда,
когда его собственная документация называет его кэшем, журналом или
производными данными, которые инструмент восстановит сам. Двойная косая делит
путь на основание и хвост: основание переносит переменная окружения
(`npm_config_cache`, `GOCACHE`, `CARGO_HOME`, `GRADLE_USER_HOME` и другие), и
разработчик, перенёсший кэш, получает своё место, а не то, которого уже нет.

**Как справочник попадает в приговор.** Строка превращается в «цепь» — путь
места, ограниченный косыми с обеих сторон, `/home/u/.npm/_cacache/`. Хозяин
цепь собирает, ядро — сверяет, и косые и делают сверку сверкой ПО
СОСТАВЛЯЮЩИМ: `/home/u/x.npm/_cacache/` цепи `/home/u/.npm/_cacache/` не
содержит, потому что перед `.npm` там нет косой. Справочник, у которого цепь не
ограничена, ядро отвергает целиком («Справочник ограничен») — сверять её как
подстроку значило бы вернуть ошибку, которую чинили 1 сентября.

**Чего справочник не может.** Он называет разряд и только его. Разрядов ему
позволено четыре — Кэш, Журнал, Сборка, Загрузка; «Крупное» решает размер, а
«Неизвестное» значит «место не нашлось», и назвать их местом ядро не даёт
(постусловие «Место обосновано»). Порогов справочник не смягчает, каталогов и
ссылок не убирает, и хранилище, адресуемое содержимым, остаётся нетронутым:
постусловие И3 сильнее любой строки файла. Инвариант И1 — «МожноУбрать» не
выходит за Кэш, Журнал и Сборку — держится ровно как прежде, сколько бы мест
файл ни знал.

<a id="защитный-список"></a>

### Защитный список

Способ сказать «это не трогай» — по пути и по разряду:

```bash
./digitdisk clean <путь> --protect ~/projects        # путь и всё под ним
./digitdisk clean <путь> --protect разряд:Загрузка   # весь разряд
./digitdisk clean <путь> --protect-file Ф            # списком из файла
```

Без ключа читается `~/.config/digitdisk/protect.conf`; строка там —
`путь|~/projects|почему` или `разряд|Журнал|почему`. Путь, написанный без
ведущей косой, защищает такую цепочку составляющих на любой глубине.

Защитный список живёт **у хозяина, а не в правилах**, и это не мелочь. Ядро
отвечает на один вопрос — чем этот путь ЯВЛЯЕТСЯ, — и каждый его ответ доказан;
«не трогай мои `~/projects`» ответом на этот вопрос не является: путь вполне
может быть кэшем, и написать обратное в справочнике значило бы завести в слой
неправду ради нужного действия. Распоряжение хозяина машины живёт там, где у
хозяина уже стоит вето, — рядом с проверками в `internal/clean`. Оттого оно
ничего и не ослабляет: список умеет только вычитать из плана, и ни одно
постусловие ядра от него не двигается. Защищённое печатается отдельным разделом
ЗАЩИЩЕНО — с правилом и строкой файла, — а не исчезает из плана молча, и не
смешивается с разделом ОТКАЗАНО: отказ значит, что два слоя разошлись и на
правила надо посмотреть, а защита значит, что правила сработали, а решение
отменил человек.

### Журнал уборки

```bash
./digitdisk history <путь>          # корень уборки, хранилище корзин или одна корзина
./digitdisk history <путь> --json
```

Что убрано, когда, сколько байт лежит в корзинах, сколько возвращено, сколько
стёрто — и чем вернуть последнее. **Между прогонами digitdisk не помнит
ничего**: всё читается из тех же `journal.json`, которые слушаются `restore` и
`purge`. Отдельная база истории была бы вторым рассказом о тех же событиях, и
разошлись бы они в первый же раз, когда корзину переставили `mv`.

«Освобождено» в этой сводке — только стёртое: перенос в корзину не освобождает
ни байта, и число, которое утверждало бы обратное, было бы неправдой о диске.

<a id="системная-корзина"></a>

### Почему не системная Корзина

Убранное уходит в свою корзину внутри дерева, а не в Корзину рабочего стола, и
причин три, из них одна — число.

**Число.** Корзина внутри дерева означает `rename(2)`: на этой машине перенос
гибибайта не укладывается в разрешение таймера (0,00 с, три прогона), потому
что байты не двигаются вовсе. Корзина за границей файловой системы превращает
перенос в копирование: то же самое на диск с `fsync` — **0,91 с на гибибайт**
(лучшее из трёх: 0,91 / 1,01 / 1,12). Цена обратимости стала бы равна объёму
уборки, на время копирования файл существовал бы дважды (то есть место надо
иметь заранее), а обрыв на середине оставил бы полфайла. И `~/.local/share/
Trash` на Linux, и `~/.Trash` на macOS — обе домашние, а убирают чаще всего с
других томов.

**Граница записи.** «Не выходит за указанное дерево» у digitdisk — свойство
самих системных вызовов: всё идёт через `os.Root`, открытый на корне, который
наружу не выпускает даже по символической ссылке. Уборка `/var/tmp`, пишущая в
`~/.local/share/Trash`, это свойство отменяет.

**Общего поведения у двух систем нет.** На Linux Корзина описана
[спецификацией freedesktop.org](https://specifications.freedesktop.org/trash-spec/latest/):
`files/` и `info/` с файлами `.trashinfo`, и та же спецификация говорит, что
домашняя Корзина принимает только файлы своей файловой системы, а для чужого
тома нужен `.Trash-$uid` в его корне — который пришлось бы создавать. На macOS
раскладка Корзины своя, а «Положить обратно» Finder держит в непубликуемом
хранилище: документированный путь туда — `NSFileManager trashItemAtURL:`, то
есть Cocoa, то есть cgo, то есть конец кросс-сборке четырёх целей с одной
машины и повторимому отпечатку. Двух систем с общим поведением здесь нет —
есть две разные Корзины и один способ соврать про освобождённое место.

Что вместо: корзина digitdisk — обычный каталог. Кто хочет отдать её системной
Корзине, отдаёт её сам, одним движением, и делает это осознанно.

### Живой экран

В терминале `digitdisk` и `digitdisk status` открывают живой экран в палитре
Digitable Focus: разделы печатного отчёта как страницы, которые продолжают
мерить. `← →` и `Tab` ходят между ними, `1`…`9` — сразу в нужный, `↑ ↓`
прокручивают длинный, `p` держит паузу, `r` меряет сейчас, `?` показывает
список подкоманд, `q` выходит.

Список по `?` только называет команды и ни одной не запускает. Этот экран —
`status`, который читает и ничего не пишет, а `clean` переносит файлы: команда,
меняющая диск, не кладётся в одно нажатие от чтения.

Везде, кроме терминала, инструмент печатает ровно как печатал. Труба, файл,
`/dev/null`, `--json`, `TERM=dumb` и пустой `TERM` получают текстовый отчёт:
экран не рисуется в то, что терминалом не является, — скрипты видят то же,
что видели всегда.

| | |
|---|---|
| `--plain` | напечатать снимок один раз, даже в терминале |
| `--live` | требовать экран: без терминала — ошибка, а не тихая печать |
| `--interval MS` | как часто экран меряет заново (по умолчанию 2000) |
| `DIGITDISK_PALETTE` | `carbon` (по умолчанию), `paper`, `signal` — палитры стека |

`NO_COLOR` уважается: экран работает, просто рисуется без цвета.

## Чего не делает

- **Не удаляет по маске и не удаляет по списку путей.** Список известных мест у
  digitdisk есть, и он ничего не удаляет: справочник называет РАЗРЯД, а убирает
  инструмент ровно то, чему решающий слой вынес приговор «МожноУбрать» — с теми
  же порогами, тем же запретом на каталоги и ссылки и тем же отказом трогать
  хранилища, адресуемые содержимым. Место в справочнике — довод, а не команда.
  Поверх этого у хозяина своё вето: каталог, символическую ссылку и недоступное
  он не тронет, даже если слой попросит, — а когда два слоя расходятся, печатает
  расхождение вместо того, чтобы действовать по нему.
- **Не удаляет одним шагом и не удаляет без спроса.** Нет ключа, который стирал
  бы без плана до и отдельного подтверждения после; `clean` сам по себе не
  трогает вообще ничего.
- **Не выходит за указанное дерево.** Все обращения к файлам идут через
  `os.Root`, открытый на этом каталоге: он разбирает путь по частям сам и наружу
  не выпускает, в том числе по символической ссылке. Корзина обязана лежать
  внутри того же дерева — корзина в стороне превратила бы каждый перенос в
  копирование через границу файловой системы, и цена обратимости стала бы равна
  объёму уборки.
- **Не удаляет рекурсивно.** `os.RemoveAll` не встречается в дереве нигде, и
  `tools/licensing.flang` роняет сборку, если встретится. Файлы уходят по
  одному, по списку в журнале; пустые каталоги — вызовом, который непустой
  каталог не трогает.
- **Не объясняет вместо того, чтобы измерять.** Где число есть — оно
  напечатано; где его нет — прочерк, а имя показателя названо одной строкой в
  конце. Почему именно нет — по `digitdisk status --why`, отдельным ключом, а
  не в середине отчёта: читателю нужно число, а не рассказ о вызовах ядра.
- **Это не форк mole**, и кода mole под GPL-3.0 здесь нет — оттуда пришла
  идея, а не код. См. [`NOTICE`](NOTICE).

## Проверки

```bash
flang io tools/licensing.flang      # копилефт, заголовки SPDX, удаление только в host/internal/clean
flang check core/disk-inventory.flang && flang test core/disk-inventory.flang
make -C core                        # проверка, печать в Go и C, сверка двух печатей
cd host && go vet ./... && go test -count=1 ./...
cd host && GOOS=darwin GOARCH=arm64 go build ./... && GOOS=darwin GOARCH=amd64 go build ./...
cd host && GOOS=darwin go vet ./...  # маковский хозяин, проверенный с машины, которая не мак
scripts/build-release.sh            # архивы, суммы, формула; заодно сверяет, что сборка повторяется
```

Сторож лицензий и сверка печати написаны на flang, а не на Python и JavaScript:
в дереве нет ни того, ни другого. Компилятор flang — один двоичный файл,
которому нужен только `cc` (`brew install flang`, `asdf`, либо
`make -C bootstrap` в клоне языка); Node он не требует.
