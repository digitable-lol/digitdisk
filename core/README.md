# `core/` — решающий слой digitdisk

Здесь живёт то, что digitdisk **решает**: к какому разряду отнести находку, что
про неё посоветовать и сколько она весит. Фактов отсюда никто не собирает —
файловую систему щупает хозяин в [`../host`](../host), а сюда подаёт значения.

## Что здесь исходник, а что вывод компилятора

| Путь | Что это | Лежит в git? | Правится руками? |
|---|---|---|---|
| `disk-inventory.flang` | **исходник.** Правила, пороги, примеры, постусловия | да | **да, только он** |
| `differential.flang` | **исходник.** Сверка двух печатей между собой | да | да |
| `out-go/` | вывод компилятора: тот же модуль, напечатанный в Go | **да**, 6 304 строки | **НЕТ** |
| `out-c/` | вывод компилятора: тот же модуль, напечатанный в C | **нет**, печатается на месте | **НЕТ** |

### `out-go/` и `out-c/` — это НЕ исходники

Это то, что напечатал компилятор flang из `disk-inventory.flang`:

```bash
flang emit --target go disk-inventory.flang --out out-go
flang emit --target c  disk-inventory.flang --out out-c
```

### Почему `out-go/` закоммичен, а `out-c/` — нет

Довод «чтобы сборка из чистого клона требовала только Go» стоял здесь с первого
дня и был **шире правды**: он не называл ни признака сборки, за которым
напечатанное вообще нужно, ни каталога, которому он не подходит вовсе. Ниже —
тот же довод, но по каталогам и числами. Все числа сняты в чистом клоне на
`AMD EPYC 7742` — на той же машине, что и замеры раскладки в
[`../ui-flang/README.md`](../ui-flang/README.md).

**Обычная сборка не читает напечатанное вообще.** Удалите `core/out-go`,
`core/out-c` и `ui-flang/out-go` целиком — и `go build ./...`, `go vet ./...`,
`go test ./...` в `host/` останутся зелёными: решающий слой стоит за признаком
`flangcore` (`host/decider_flang.go`, `host/internal/coreflang/bridge.go`), а
без признака собирается заглушка. Значит «только Go» — это НЕ про `go build`.

**Про что оно на самом деле — про выпуск.** `scripts/build-release.sh` собирает
все четыре цели с `-tags flangcore` (строка 119) и падает на самопроверке, если
ядра на flang в двоичном файле не оказалось (строка 234). Компилятор flang он
не зовёт ни разу. То же и у того, кто собирает себе: `cd host && go build -tags
flangcore`. Уберите `out-go/` из дерева — и этот путь отвечает

```
flangprogram@v0.0.0: replacement directory ../core/out-go does not exist
```

то есть выпуск начинает требовать компилятор.

**Чего это стоило бы, замерено.** Компилятор — действительно один двоичный из
одного `cc`, и это не значит «дёшево»: `make -C bootstrap` на v0.7.10 — это
38 МБ C в четырёх единицах трансляции, **5 мин 12 с** одним вызовом, **1 мин
54 с** при `-j4` и **1 мин 48 с** при `-j8` (единиц четыре, больше ядер занять
нечем), пик памяти **1,7 ГиБ**. Готовый двоичный — 21 МБ, зависимости `libm` и
`libc`. Число это не падает, а растёт: язык обещает `make -C bootstrap -j8`
«около минуты», здесь вышло почти вдвое больше. Именно поэтому довод не
отменён — 6 304 строки в git против двух минут и полутора гигабайт на каждой
машине, которая собирает выпуск.

**А `out-c/` этим доводом не покрыт ничем, и потому из git убран.** Его не
читает ни `host/`, ни `scripts/`; единственный, кто его зовёт, —
`differential.flang` через `out-c/flang_cli`, а цель `сверка` зависит от
`печать`, которая начинается с `rm -rf out-go out-c`. То есть закоммиченные
12 130 строк C не читал никто и никогда: любой прогон, которому они нужны,
печатает их заново, и у него уже есть компилятор. Теперь они печатаются на
месте и игнорируются (`core/.gitignore`).

Напечатанного в git было 36 487 строк из 78 376 — **46,6 %** дерева, больше,
чем весь рукописный хозяин (33 467 строк `host/*.go`). Стало 24 357 из 66 296,
**36,7 %**: `core/out-go` (6 304) и `ui-flang/out-go` (18 053), и у каждого —
свой признак сборки и свой прогон, который без него краснеет.

**Цена этого решения.** Вывод обязан оставаться в согласии с исходником.
Поэтому правка руками внутри `out-go/` или `out-c/` — **дефект, а не правка:**
`make -C core` начинается с `rm -rf out-go out-c` и сотрёт её молча. Меняется
поведение ядра — меняется `disk-inventory.flang`, потом печать, потом оба
изменения идут одним коммитом.

**Почему имена файлов там `opis_diska.*`, а исходник `disk-inventory.flang`.**
Имя выходного файла даёт **имя модуля** внутри исходника (`модуль «Опись
диска»`), а не имя файла. Так печатает компилятор; переименовать вывод значило
бы править его руками.

## Порядок работы

```bash
make -C core            # всё сразу: проверка, печать, сверка
make -C core проверка   # flang check + flang test: типы, завершаемость, 115 примеров
make -C core печать     # перепечатать out-go и out-c целиком
make -C core сверка     # 240 входов через оба напечатанных кода; расхождений должно быть 0
```

Компилятор flang — один двоичный файл, которому нужен только `cc`:
`brew install digitable-lol/tap/flang`, `asdf`, либо `make -C bootstrap` в клоне
языка (что это стоит — числами выше). Node он не требует, и в этом дереве нет ни
JavaScript, ни Python.

## Почему ядро не ходит в файловую систему само

В языке 22 поручения ввода-вывода, и обход каталога среди них есть. Ядро всё
равно остаётся чистым — по причинам, которые замерены, а не предположены; они
выписаны в шапке `disk-inventory.flang`. Коротко: отклик «Перечислено» несёт
только имена, без размеров; добыть размеры можно лишь запуском процесса
(8,82 мс на запуск — 16,5 минуты на дерево из 111 986 записей против 3,39 с);
а программа с объявлением `план` печатается лишь одной целью из восьми, то есть
самостоятельным двоичным файлом такой digitdisk уже не станет.
